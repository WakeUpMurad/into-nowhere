# Платежи: контракт и следующий этап

Первая версия Go API работает в демонстрационном режиме. Ключи провайдера не нужны. Сервер не создаёт заказов, финансовых записей или платёжных сессий и не подтверждает оплату по нажатию кнопки.

## Запуск

Из `apps/api`:

```sh
go run ./cmd/server
go test ./...
```

API слушает только `127.0.0.1:8080`. Переменная `PORT` позволяет выбрать другой порт от 1 до 65535. Веб-приложение обращается к `/api` через прокси своего сервера разработки. Для публикации понадобится HTTPS и настроенный reverse proxy; открытие локального Go-сервера в интернет не предусмотрено.

## API

`GET /api/health` → `200`:

```json
{"status":"ok"}
```

`GET /api/config` → `200`:

```json
{
  "mode": "demo",
  "currency": "USD",
  "minAmountMinor": 100,
  "paymentsEnabled": false,
  "paymentMethods": [],
  "charitySharePercent": 25
}
```

`POST /api/payments/create` принимает только три поля:

```json
{"amountMinor":"100","currency":"USD","intention":"gratitude"}
```

`amountMinor` — строка с целым числом центов, минимум `100` ($1). Использование строки сохраняет точность сумм при передаче из JavaScript. Допускаются до 30 цифр без знака, пробелов, экспоненты и ведущих нулей. Это техническое ограничение входных данных; реальные ограничения провайдера будут определены при его подключении. `intention` принимает `wealth`, `health`, `success`, `love` или `gratitude`. Валюта пока только `USD`.

В демонстрационном режиме любой корректный запрос возвращает `503`:

```json
{"code":"PAYMENTS_NOT_CONFIGURED","message":"Real payments are not connected. No money has been charged."}
```

Ошибки валидации возвращают `400` и соответствующий `code`: `INVALID_REQUEST`, `INVALID_AMOUNT`, `INVALID_CURRENCY`, `INVALID_INTENTION`. Неизвестные поля, включая произвольный `returnUrl`, отклоняются. Предел тела запроса — 4096 байт (`413 REQUEST_TOO_LARGE`). Неверный метод возвращает `405 METHOD_NOT_ALLOWED` и заголовок `Allow`. Несуществующий маршрут возвращает `404 NOT_FOUND`. Обработчик webhook ещё не создан.

## Что потребуется для настоящей оплаты

После одобрения продавца платёжным провайдером нужно получить актуальную документацию, тестовые реквизиты и доступные для этого продавца методы оплаты. Apple Pay и Google Pay должны определяться по разрешённым методам провайдера и поддержке на устройстве пользователя. Интерфейс не должен показывать их как подключённые до этого этапа. Ключи остаются на сервере.

Для следующего этапа понадобится постоянная база заказов и платежей. Сервер самостоятельно фиксирует сумму, валюту, намерение и получателя. Создание оплаты требует ключа идемпотентности: повтор одного запроса не должен создавать второе списание. Создание заказа и его переходы между состояниями сохраняются атомарно.

Адреса возврата задаются сервером для заранее разрешённых доменов. Клиент не может передать произвольный адрес редиректа. Успешный возврат браузера от провайдера не доказывает оплату: статус `paid` появляется только после проверки серверного уведомления по протоколу провайдера или его серверного API. Проверяются подпись/подлинность, идентификатор заказа, сумма, валюта, продавец и окончательный статус. Повторное или пришедшее не по порядку уведомление обрабатывается идемпотентно и не создаёт повторной финансовой записи. Световой эффект может завершаться как демо-жест; подтверждение оплаты должно быть отдельным достоверным состоянием.

Затем понадобятся сверка с отчётами провайдера, возвраты, журнал операций, защита от частых запросов и ограниченные права доступа к платёжным данным. Полные реквизиты карт и платёжные токены в журнал не записываются. Эти части ещё не реализованы.

## Обещание о 25% и точность учёта

Обещание проекта: **25% исходной суммы оплаты до комиссии направляются на прямую помощь нуждающимся**. Комиссии провайдера и расходы сервиса относятся к оставшимся 75% и не уменьшают обещанную долю помощи.

У одной оплаты доля может составить дробную часть цента: например, 101 цент × 25% = 25,25 цента. При подключении учёта нужно хранить эту долю точно — в целых четвертях цента либо другой фиксированной точности — и агрегировать до фактической выплаты. Округление каждой оплаты вниз уменьшит обещанные 25%, поэтому так делать нельзя. Непереведённый остаток и правило итогового округления должны быть видны в отчёте.

Правила для отмен, полных/частичных возвратов и чарджбэков ещё не согласованы. До включения платежей нужно определить, как они влияют на долю помощи, уже перечисленные средства и публичный отчёт. Частота отчётов и сроки прямой помощи также требуют отдельного решения. Персональные истории получателей публикуются с их согласием; предоставление помощи не должно зависеть от согласия на публикацию.
