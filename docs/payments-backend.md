# Сервер оплаты: демонстрация и подготовленный Epoint

Настоящий маршрут первого запуска проекта — TON через отдельный Cloudflare Worker, опубликованный вместе с основным сайтом. Развёртывание, подтверждение и обязанности оператора описаны в [руководстве TON](ton-payments.md). Описанный здесь Go API — подготовка для последующего карточного эквайринга Epoint. Аккаунт продавца, ключи и договор пока не получены; публичное демо не превращается в подключённый эквайринг от наличия этих исходников.

## Запуск и закрытый режим по умолчанию

Из `apps/api`: `go run ./cmd/server`; проверки: `go test -race ./...`.

По умолчанию сервер слушает `127.0.0.1:8080`, реальных способов оплаты нет, корректный `POST /api/payments/create` возвращает `503 PAYMENTS_NOT_CONFIGURED`. Демонстрация не создаёт заказов, файлов учёта или запросов провайдеру. `PORT` меняет локальный порт. Для внешнего размещения адрес задаётся отдельно, например `LISTEN_ADDR=0.0.0.0:8080`, за HTTPS-прокси.

Сервер читает переменные окружения процесса. Пример названий находится в `apps/api/.env.example`; файл не загружается автоматически. Секреты нельзя помещать в Vite, Git или сообщения чата.

Режим `live` включается только при полном наборе:

- `EPOINT_PUBLIC_KEY`, `EPOINT_PRIVATE_KEY` — серверные реквизиты одобренного продавца;
- `PAYMENT_MERCHANT_APPROVED=true`, `PAYMENT_CURRENCY_APPROVED=true` — подтверждение реально полученного допуска, а не способ обойти его;
- `PAYMENT_CURRENCY=AZN` либо `USD`, `PAYMENT_MIN_AMOUNT_MINOR`, `PAYMENT_MAX_AMOUNT_MINOR` — согласованные валюта и границы в целых сотых;
- `PAYMENT_PUBLIC_BASE_URL` — доверенный HTTPS-адрес нашего сайта без параметров и фрагмента;
- `PAYMENT_MERCHANT_NAME`, `PAYMENT_SUPPORT_EMAIL` — реальные данные продавца и поддержки;
- `PAYMENT_DATA_PATH` — файл на постоянном диске, доступном только серверу.

Неполная или некорректная конфигурация остаётся демо. Ошибка открытия хранилища при полной конфигурации останавливает запуск: сервер не должен принимать оплату без постоянного учёта. GitHub Pages Go не запускает. Бесплатный сервер с временным диском не подходит для этого файла.

## Публичный контракт

`GET /api/config` возвращает прежние поля `mode`, `currency`, `minAmountMinor`, `paymentsEnabled`, `paymentMethods`, `charitySharePercent`, плюс `maxAmountMinor` (строка или null). В `live` присутствуют `provider: "epoint"`, `merchantName`, `supportEmail`, а способы оплаты содержат только `card`. Кошельки Apple Pay/Google Pay отдельно не объявляются подключёнными без проверки аккаунта.

`POST /api/payments/create` принимает JSON `amountMinor` (строка целых сотых), `currency`, `intention`, необязательный `locale` (`en`, `ru`, `az`). Намерения: `wealth`, `health`, `success`, `love`, `gratitude`. Неизвестные поля, лишние JSON-объекты, числа вместо строки суммы и суммы вне утверждённых границ отклоняются. В live обязателен заголовок `Idempotency-Key`: 1–128 букв, цифр, дефисов или подчёркиваний. Клиент создаёт случайный ключ и повторяет его только для того же заказа.

Ответ содержит `orderId`, `readToken`, `checkoutUrl` (строка либо null), `status` (`pending`, `paid`, `failed`, `refunded`), `amountMinor`, `currency`, `charityQuarterMinor`, `confirmation` (null либо `provider`). Новый checkout обычно возвращает 201; повтор — 200; неизвестный результат внешнего запроса или отсутствие безопасного URL — 202 с pending. Повтор ключа с другой суммой, валютой, намерением или языком даёт 409. Один и тот же ключ не повторяет запрос создания в Epoint, в том числе после перезапуска.

`GET /api/payments/{orderId}` требует `Authorization: Bearer {readToken}`. Ответ не содержит сам токен. Если известна транзакция Epoint, сервер перепроверяет статус с ограничением частоты раз в пять секунд на заказ. Чужой/неверный токен не раскрывает наличие заказа. Публичного списка заказов нет.

Адрес возвращения создаётся сервером как доверенный адрес с `#payment={orderId}&token={readToken}`. Фрагмент не отправляется веб-серверу браузером; фронтенд должен убрать его из адресной строки после чтения. Возврат с checkout, любые параметры `paid=true`, собственное сообщение клиента и завершение 3D-жеста не подтверждают списание.

## Проверенный протокол Epoint

Использован [официальный PDF Epoint](https://epointbucket.s3.eu-central-1.amazonaws.com/files/instructions/API%20Epoint%20en.pdf), проверенный 5 октября 2026 года. Запросы — POST-формы к `https://epoint.az/api/1/request` и `https://epoint.az/api/1/get-status`:

- `data = base64(UTF-8 JSON)`;
- `signature = base64(raw SHA-1(private_key + data + private_key))` — именно протокол Epoint, не HMAC;
- создание передаёт `public_key`, точное десятичное `amount`, `currency`, `language`, `order_id`, описание и фиксированные адреса возврата;
- проверка статуса передаёт `public_key` и `transaction` с той же подписью.

`result_url` необходимо настроить в кабинете Epoint на публичный `/api/payments/epoint/callback`; это не выдуманное дополнительное поле запроса создания.

Callback принимает form-поля `data` и `signature`. Подпись проверяется постоянным по времени сравнением до декодирования JSON. Проверяются заказ, транзакция, точная сумма и `operation_code=100` (платёж пользователя, а не регистрация карты 001). Затем сервер запрашивает аутентифицированный статус Epoint и повторяет сверку. Только `success` подтверждает paid. `new`, `server_error` и неизвестные состояния остаются pending; проверенный `failed`/`error` может установить failed; `returned` фиксирует refunded. Поздний отказ не отменяет paid, а повтор старого success не отменяет refunded.

В документированных callback и ответе get-status нет поля currency. Валюта связывается с неизменяемым заказом и исходным подписанным запросом; если провайдер вернёт поле currency, его тоже проверяем. PDF указывает AZN, более новые материалы допускают другие валюты: USD требует отдельного подтверждения аккаунта.

Ответ создания `status=success` означает создание checkout, а не оплату. Редиректы разрешены только на точный HTTPS-хост `epoint.az`, без userinfo и нестандартного порта. Если фактический аккаунт возвращает страницу банка на другом домене, этот URL не публикуется. Нужна проверка домена у провайдера и явное дополнение разрешённого списка; нельзя разрешать произвольный redirect.

## Постоянный учёт и точность

Используется одно-процессное JSON-хранилище со взаимным исключением, межпроцессной блокировкой, записью во временный файл, fsync, атомарным переименованием и синхронизацией каталога. Второй процесс отказывается открыть тот же файл. Файл содержит токены чтения и должен оставаться приватным; `apps/api/data/` исключён из Git. Эта реализация подходит для небольшого сервиса на одном сервере. Для нескольких экземпляров и существенного оборота нужна транзакционная БД.

Заказ записывается до внешнего запроса. При сетевом обрыве результат остаётся pending: сервер не предполагает отказ и не создаёт повторную транзакцию. Если транзакция не была получена и callback не пришёл, требуется сверка с провайдером; автоматический новый запрос по тому же ключу запрещён.

Обещание проекта — **25% исходной суммы до комиссии**. `charityQuarterMinor` — целый числитель в четвертях минимальной денежной единицы: при оплате 101 цента записывается `101`, что означает 25,25 цента помощи. Суммирование производится до округления фактического перечисления. Плавающая точка не используется. Это обязательство учёта, не подтверждение фактической помощи или перевод средств нуждающимся.

## Проверки и оставшиеся условия активации

Автотесты проверяют закрытый демо-режим, точность сумм, повторные и одновременные создания, потерю ответа и перезапуск, подпись и несовпадение суммы/валюты/транзакции, повторные callback, неподтверждённый возврат браузера, сохранение receipt, межпроцессную блокировку и отказ от посторонних redirect. Провайдер в тестах подменяется контролируемым транспортом; настоящих списаний нет.

До включения карточного маршрута нужны реальные договор и ключи, утверждённые валюта/лимиты/домены, настройка callback, публичные правила и доступная поддержка, тестовый прогон протокола, затем разрешённая небольшая реальная оплата и возврат. Запрос возврата, частичные возвраты, полный административный журнал, автоматическая сверка отчётов и защита от массовых запросов в этой версии не реализованы. Правила помощи при возвратах/спорах и частота отчётов требуют отдельного решения перед активацией.
